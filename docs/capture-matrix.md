# Duo capture matrix

Use one current simulator build and a synthetic fixture for every surface review. The shared Mac runs **one simulator only**. Reserve its exclusive capture slot before running this script. Never overlap a native test run or boot a second device for captures.

```sh
scripts/capture-matrix.sh --screen library --state populated
```

The command installs `DerivedData/Build/Products/Debug-iphonesimulator/GistPad.app`, records build/device metadata and display enumeration, and captures cover/open x light/dark x Large/AX3. It defaults to the shared **GistPad Intelligence** Duo (`D121BF28-CFCF-4020-802D-2C81D38F12E2`), which must already be booted. It never boots a simulator automatically. `CAPTURE_DEVICE` or `--device` can name a replacement only after the shared device is shut down and the slot is reassigned. `--contrast both` adds eight increased-contrast captures. It restores the simulator's appearance, contrast and content-size preferences on exit. It does not erase application data or change a hardware device.

`simctl` exposes `primary` (cover) and `primary-1` (inner), but has no public fold/posture command in Xcode 27.1. The script therefore pauses for an actual posture change in Device Hub before each group. Select the assigned shared Duo in Device Hub's sidebar, then use its **Closed** or **Open** posture button. Capturing a different framebuffer alone is not evidence that the app adapted to that posture.

For background automation, supply an absolute `--posture-hook` executable accepting the simulator UDID and `cover`/`open`, or run one already-configured pose with `--pose cover --posture-ready`. The caller is responsible for verifying the posture. Never label a resized window or inactive framebuffer as a folded/open app.

## App route contract

The app receives `--capture-screen NAME --capture-state NAME` on each launch. Capture routes must be debug-only, use synthetic content and avoid connecting to an account. Library, note and editor routes should preserve the same deterministic fixture. Relevant empty/error/sheet states are separate named fixture states. Unknown routes must show an explicit diagnostic rather than silently opening a default screen.

Launches restart the app to make each capture independent. Do not run against an active editing session. A real keyboard and continuity sequence are separate requirements where relevant.

Library, note and Photos routes also receive a unique `--capture-ready-token`. The Debug fixture records that token in the app's temporary container only after the Library appears, WebKit reports a completed render, or the Photos fixture and retained source view attach. The script waits up to 45 seconds and fails without a screenshot if readiness is absent. This prevents a loading or cold, blank view from silently becoming evidence. A preview error is itself a ready error surface and remains recorded in the readiness JSON. Other routes use the configured settling interval and still require inspection.

For the focused reading review, pass `--screen note --capture-reading-fixture`. This loads `PreviewFixtures.readingPolish` through the real native note screen, with outline, calculations, neutral and authored diagrams, aligned tables and disclosure. The readiness JSON identifies `reading-polish`, and the build metadata records the flag. Use a separate evidence directory and frozen build from the baseline notebook matrix. Launching the Debug app with `--capture-reading-fixture` alone also selects the synthetic note route, never a live account.

`--capture-screen scroll-edges --capture-state preview|source` uses the production note chrome with a long, in-memory page. On the 466-point display, it positions a middle heading partly beneath the top bar while prose continues beneath the bottom safe area. Its readiness token is written only after the actual native content offset, content size, viewport and insets remain unchanged for at least 20 display frames and 350 ms. Source is in Edit with its keyboard dismissed. The `source-keyboard` state instead requires native focus, the actual software keyboard frame and an attached formatting accessory. The JSON records their geometry alongside target/actual offsets, heading and navigation-bar positions, viewport, insets, appearance and text size. Capture Light and Dark at Large directly after this marker, without substituting a fixed render delay. These resting images prove visible underlap, not bounce, fold continuity or physical-device behavior. Native bottom effects belong to overlapping app chrome, not the home indicator alone.

The accepted v1 Source stops above its real keyboard accessory. The `source-keyboard` capture verifies that geometry, not a continuous soft bottom edge through the capsule. Keyboard-dismissed Source/Preview retain their accepted native top-bar underlap.

`SourceKeyboardHostTests` independently checks final-line typing and native end-scroll reachability at Large and AX3. It hosts the production note and retained Source, measures actual caret/glyph rectangles against navigation and the accessory, and rejects any editor extension behind the system keys. Typing must reveal the caret without a corrective test scroll. End scrolling must expose the last line without changing selection, source bytes or generation. These tests require settled real-keyboard geometry and do not depend on the capsule-underlap prototype.

`--screen library --state tag-audit` exercises a long full-name label, two-label overflow, white, black, saturated yellow and missing tag colors. The removed `--screen note --state today` landing is replaced by `--capture-screen today --today-fixture missing|existing|cold|signed-out|retry`, which uses the real workspace and cached daily-note staging against an isolated in-memory store. Missing and existing scenarios support a real Today tap. Cold and Retry stay keyboard-free, and signed out shows the existing sign-in path. No account write is possible. `--screen note --state tag-editor` opens the native Tags sheet with local-only choices and an intentionally failing synthetic save callback for Retry review. `tag-readonly` opens its nonmutating version. Read-only source fixtures pass disabled task-edit capability to the preview. Tag metadata capability remains independent of GitHub source access. These use synthetic values and the same readiness contract.

`--screen photos` supports `editor`, `insert`, `notice`, `notice-end`, `picker`, `pending`, `multiple`, `details`, `details-end` and `unpublished`. It uses in-memory drafts, synthetic image bytes and an offline-only upload transport. Multiple-photo fixtures inject a synthetic network failure so full status and Retry actions can be inspected in Details. The inline surface is one rounded, secondary-background disclosure summary at every text size, with no nested scrolling or inline recovery buttons. It shows the count and failure status where space allows, then count plus an issue indicator, retaining the full accessible status. Standard sizes may show a thumbnail. Full photo rows, accent-colored recovery and removal menus live in the large native Photos sheet. Opening it dismisses the keyboard without changing source, selection or Undo. Choose Another closes Details before presenting the picker. Upload and publication timing are unchanged.

The editor requests focus once it attaches, but never behind the notice or picker. `insert` waits up to five seconds for the actual accessory button to attach, lets its keyboard anchor settle, then invokes the native primary action, not a replica menu. The Photo action always carries the subtitle "Public, even in a secret gist", without a separate disclosure command. The full first-use notice puts its untruncated headline in the scrolling content.

This route uses the same per-launch readiness marker as Library and reading. Its JSON records actual window dimensions, text-size category, source focus and keyboard height from native frame notifications. `multiple` requires the real summary's accessibility frame, source focus and at least 150 pt of software keyboard to settle for at least 20 samples and 350 ms within 12 seconds. `details` and `details-end` first activate that actual disclosure's native primary action, then require the source keyboard to be dismissed and the native sheet's scroll geometry and requested position to settle by the same deadline. `notice-end` and `details-end` require content-end visibility and record viewport height. Details end also verifies the last native recovery target is at least 44 pt high and above the safe area. The removed inline-scroll routes must not be used for current acceptance.

Photos acceptance requires whole-display summary screenshots with the actual system keyboard and accessory, plus Details start/end at Large and Light/Dark AX3. Use `--capture-accent '#FACC15'` to verify saved-yellow controls. `NotebookPhotoTests/shelfKeepsWritingSpaceAndAccessibilityDetails` records only its app window, not the system keyboard window. It verifies the disclosure's 44-pt target, count and accessible failure status, no inline scroll view, standard thumbnail containment and two scaled writing lines plus source top padding below the actual navigation bar. The summary stays within the normal 128-pt / accessibility 180-pt caps, including its external padding, and becomes shorter when needed to preserve writing space. The probe activates the disclosure, reaches the last Details recovery action above the safe area, checks saved-accent pixels and preserves source, selection and native Undo through dismissal. Run the whole serialized `NotebookPhotoTests` suite, which owns the shared fake transport, rather than splitting concurrent Photos suites.

Evidence contains `matrix.tsv`, `build.txt`, `displays.txt`, `settings-before.txt`, readiness JSON and individually named PNGs. Submit the PNGs as channel attachments. Inspect them for correct route, active screen, fixture, keyboard and clipping before asking for Designer sign-off. The capture command does not itself certify accessibility, continuity, frame time, physical fold behavior or design approval.
